# Phase 3 回顧

Action & Consequence Engine v0.3

這份文件檢討**流程**，不檢討人。所有問題都以「什麼樣的做法讓這件事得以發生」來描述 —— 目標是讓下一個階段不要重蹈，不是追究誰的責任。

寫完不再更新。

---

## 1. 摘要

Phase 3 重寫了整條 action 結算路徑，engine.py 從 486 行降到 233 行，十種 action type 走同一條路，reference 的每一筆 event 與 Phase 2 相同，沒有任何一輪重工。

但這一輪最重要的發現不在 Phase 3 自己的程式碼裡：**Phase 2 留下了兩個潛在缺陷，Phase 2 的測試全綠、反向驗證也做了，卻都沒抓到。** 一個是節點位置被拆成字元，一個是 tick 0 的事件不被重放。兩者都是 Phase 3 第一次用「不一樣的資料」走過 Phase 2 的程式碼時才浮現。

**核心教訓：測試只能證明它涵蓋的資料是對的。判斷一個變異是否「等價」、判斷一段程式是否「被測過」，都要問測試資料有沒有涵蓋讓結果不同的情況。**

## 3. 做得好的地方

### 「逐筆相同」取代「數量相同」

前兩個 Phase 的回歸基準是勝負、事件數、型別順序。這次重寫的是**產生 event 的程式碼本身**，數量對不代表內容對。所以在動手前先把 Phase 2 的 result package 去掉 uuid 存起來，改完之後整包比對。

第一次比對就完全相同。這讓後面所有的重構都有底氣 —— 任何一個欄位、一個 tag、一個 affected location 不同，都會被看到。

### 把基準釘進 repo

`tests/fixtures/reference_trace.json` 讓這個比對不再依賴某次 session 暫存的檔案。它的 digest 在 Phase 2 程式碼與 Phase 3 程式碼上算出同一個值，這是「行為不變」最強的證據，也是之後每個 Phase 的回歸基準。

### Frozen Interface 附行為（Phase 2 改法 2）

這次每個函式都寫了一行行為，十種 action type 各寫了一行語意。寫 handler 時直接照著寫，沒有出現 Phase 2 那種「同一個參數兩種理解」。

### AST 守護 + 守護的守護

「handler 不能改世界」用 AST 檢查。檢查寫完後，另外寫了六個測試，各放一種違規寫法進去確認會被抓到 —— 這是 Phase 2 改法 1（守護型測試也要反向驗證）的直接應用，而且做成了永久測試，不是一次性的手動驗證。

## 4. 出了什麼問題

### 問題 1：Phase 2 的兩個潛在缺陷（最嚴重）

```text
Event.to_dict()     list("depot") → ["d","e","p","o","t"]
                    Phase 2 的測試驗證手寫 dict，沒有一筆真的 Event 帶節點位置走過 to_dict()
rebuild_world()     只重放起始 tick 之後的事件；初始快照在 tick 0 事件之前擷取
                    Phase 2 的測試資料（reference）沒有 tick 0 的事件
```

第二個更值得檢討：Phase 2 反向驗證時，「`<=` 改成 `<`」存活了，當時判定為等價變異，還在 docstring 寫了理由。**判定的依據是「現有測試都過」，而不是「找不到讓兩者不同的輸入」。**

### 問題 2：stash 切版本後跑在舊 bytecode 上

兩個版本的 `scenario.py` 大小相同、在同一秒內改寫，Python 沿用了舊的 `.pyc`。70 個測試失敗，查了一輪才確認程式碼沒問題。

### 問題 3：語意的偏離到整合才發現

withdraw 的同陣營、supply 的目標活著，都是寫 handler 時順手加的。Phase 2 改法 3 要求「每步 commit 前對照第 6 節」，實際只對照了簽名。

### 問題 4：步驟 A 與 B 無法分開

issue 規劃了 A（資料形狀）與 B（框架）兩步。實作時發現契約一改，舊 resolver 就產生不出新形狀的 Consequence，兩步之間沒有能全綠的中間狀態，只好合成一個 commit。開設時沒有想到這一點。

## 5. 根本原因

### 成因 1：測試資料只來自 reference scenario

Phase 2 引入了 graph 與 tick 0 這兩個新維度，但測試 event sourcing 時用的是 reference run —— grid、從 tick 1 開始。**新能力用舊資料測，新維度就沒被測到。** 手寫 dict 的測試則繞過了真正產生資料的程式碼。

### 成因 2：「等價」的判定方式錯了

等價變異的定義是「不存在任何輸入讓兩者行為不同」。Phase 2 的判定是「現有測試分不出兩者」—— 那只證明測試不夠，不證明等價。

### 成因 3：對照第 6 節的清單只有簽名欄

Phase 2 改法 3 的措辭是「簽名與行為和第 6 節一致」，但實際執行時只比了簽名，因為簽名是可以機械比對的，語意要讀。

### 成因 4：拆步驟時沒有檢查中間狀態

開設時依「資料 → 框架 → 擴充」拆步驟，沒有問「每一步結束時，品質閘門能不能全綠」。

## 6. 下一階段要改的事

### 改法 1：新能力用新資料測

每個 Phase 新增一個維度（新的空間、時間、資料型別、邊界值）時，至少一個測試要用**觸發那個維度的資料**走過**真正產生資料的程式碼**。不手寫被測函式的輸出。

### 改法 2：判定等價變異要找反例

變異存活時，先試著構造一個讓原版與變異版結果不同的輸入。構造得出來 → 那是測試缺口，補測試；構造不出來，且能說明為什麼 → 才判定等價、簡化程式碼。

### 改法 3：語意對照與簽名對照分開做

每步 commit 前的對照分兩項：簽名（機械比對）與語意（逐條讀第 6 節的行為描述，對照 validate / resolve 的每個分支）。多出來的規則寫進 ADR，或拿掉。

### 改法 4：拆步驟時寫下每步結束的綠燈狀態

開設時每個步驟寫一句「這一步結束時，哪些測試是綠的」。寫不出來的步驟，就和下一步合併。

### 改法 5：stash 切版本後清 bytecode

```bash
git stash && find . -name __pycache__ -prune -exec rm -rf {} + && <跑測試> && git stash pop && find . -name __pycache__ -prune -exec rm -rf {} +
```

## 7. 沒有結論的一項

**observe / supply / repair 已經登記在軍事線，但沒有任何 policy 使用它們。**

它們有完整的測試，但只在 logistics fixture 上被手動呼叫。tactical policy 只會 move 與 attack；讓它使用其他 action 會改變模擬結果，超出 Phase 3「行為不變」的前提。誰來第一個使用它們 —— Phase 6 的 actor 接入，或 Phase 13 的 domain pack —— 還沒有定論。

---

## 8. 一句話

> Phase 3 把結算路徑整條重寫而 reference 的每一筆 event 都沒變，因為這次的回歸基準是「逐筆相同」而不是「數量相同」—— 但它也揭露了 Phase 2 兩個全綠、反向驗證過卻仍然存在的缺陷：新能力用舊資料測、「現有測試分不出來」被當成「等價」，所以測試資料要涵蓋新維度，判定等價要找反例。
