# Phase 9 回顧

Failure Exploration Engine v0.9

這份文件檢討**流程**，不檢討人。所有問題都以「什麼樣的做法讓這件事得以發生」來描述 —— 目標是讓下一個階段不要重蹈，不是追究誰的責任。

寫完不再更新。

---

## 1. 摘要

Phase 9 交付了八個 failure variable、通訊失效的 fault injection、壓力探索、純函式的分析、四個輸出與第 13 份契約。沒有惡化時模擬不變，沒有任何一輪重工。

這一輪最有價值的一步發生在寫程式之前：**開設時先量**。基線只有 63% 不被判 fail、壞天氣反而讓存活率上升、替代部署撐到 83% —— 這三個數字讓「失敗」用 profile 的 verdict 定義、讓 sensitivity 允許為負、讓替代方案用部署來表達。如果先寫程式再看數字，至少其中一個會被當成 bug 去「修」。

另一個值得記下的是：Phase 3 回顧的「判定等價要找反例」第一次在同一個 Phase 裡直接找出兩個測試缺口。

**核心教訓：在凍結設計之前，先用現有系統量出要處理的數字；數字會告訴你哪些「看起來不對」的結果其實是對的。**

## 3. 做得好的地方

### 開設前先量

三個數字直接改變了設計：

```text
基線 63%          → 失敗由 profile 定義，不另訂；fails_without_stress 成為正式欄位
天氣 93%          → sensitivity 允許為負，而且這被寫成一個「發現」而不是錯誤
替代部署 83%      → 替代方案用版本資料夾裡的部署變體表達，而且確實有差
```

### 惡化是 scenario 層的事

每個變量把 scenario 變成一個新版本，再交給完全沒改過的 engine。engine 唯一的配合是 fault injection，而且沒有 faults 時一次都不會抽 fault_rng。結果：惡化 run 自動擁有 Phase 8 的 reproducibility 區塊與版本紀錄，不需要任何額外工作。

### 分析與模擬分開

analysis.py 是純函式，21 個測試全用手造的 run。邊界情況（負的 sensitivity、基線就失敗、同分、四種替代方案判斷）都能精確構造，不必找「剛好會產生這種結果的 seed」。

### Phase 8 的改法用上了

```text
改法 3（版本欄位在第一個 commit 就到位）   兩個替代方案的 version_control 在 fixture commit 就寫好，
                                          並當場用 compare_scenarios 驗證一致
改法 4（估計 fixture 的連帶範圍）          issue 第 2 節寫明「只改 v0.1 自己」，實際也是
```

## 4. 出了什麼問題

### 問題 1：驗證後的設定少了預設值

`check()` 只回傳提供的欄位。這是 Phase 1 為了「驗證不改變形狀」做的設計，對 scenario 正確；但對有預設值的設定，每個使用者都得記得自己補。explore 第一次就 KeyError。Phase 7 的 profile 沒踩到，只是因為檔案剛好寫滿了每個欄位 —— 一個靠運氣避開的地雷。

### 問題 2：比較把「請求」當成「世界」

compare_scenarios 的類別在 Phase 8 設計時包含了 failure_exploration，因為 Spec 把它列在 scenario 裡。直到 v0.1 真的有了這個區塊、v0.2 沒有，才發現它不該被當成世界的變化。

### 問題 3：兩個測試缺口

同分規則與基線比較都有測試，但測試資料讓規則「可有可無」。這次靠反向驗證抓到；如果沒做，兩條規則可以被任何人刪掉而不被發現。

### 問題 4：測試與文件裡的小錯

測試預期值寫錯一次、註解說得太滿一次、文件的 run 數寫錯一次。都在推送前修正，但說明「寫得快」會在小地方付代價。

---

## 5. 根本原因

### 成因 1：「驗證不改變形狀」與「預設值」之間沒有約定

契約有預設值，但驗證函式刻意不填。兩者各自都對，合在一起就是「預設值只存在於文件裡」。沒有一個地方規定使用者該怎麼取得預設值。

### 成因 2：比較的類別是照 Spec 的位置分的，不是照語意

failure_exploration 在 Spec §3.3 的 scenario 裡，所以被歸進比較類別。但「放在哪裡」與「是不是世界的一部分」是兩回事。

### 成因 3：測試資料是「隨手」選的

同分測試用的兩個變量名，是寫的時候想到的頭兩個。沒有人問「這組資料能不能區分有這條規則與沒有這條規則」。

## 6. 下一階段要改的事

### 改法 1：有預設值的設定，提供「完整化」函式

任何會被程式讀取的設定型契約（profile、exploration、之後的 batch 設定），在契約旁邊提供一個回傳「所有欄位都在」的函式，或在使用處明確補值並有測試覆蓋「欄位省略」的情況。

### 改法 2：比較與雜湊的範圍依語意決定

決定「什麼算 scenario 的變化」「什麼進 input_hash」時，逐欄問：這會改變模擬出來的世界嗎？不會的（請求、註解、設定）不進比較。

### 改法 3：每條規則的測試資料要能「區分有無」

寫一條規則的測試時，先問：如果把這條規則拿掉，這組資料的結果會不同嗎？不會，就換資料。反向驗證是事後檢查；這是事前設計。

### 改法 4：開設前的測量寫進 issue

這次的「開設時的測量」被寫進了 issue 第 1 節，效果很好。之後每個 Phase 開設時，凡是設計依賴現有系統的行為，都先量、寫進 issue，再凍結設計。

## 7. 沒有結論的一項

**變量是近似。**

sensor_failure 是「己方命中率下降」，weather_degradation 是「全體命中率下降」，civilian_pressure 是「己方起始 hp 下降」。它們能回答「如果命中率下降，方案會怎樣」，但不能回答「如果感測器壞了，方案會怎樣」—— 那需要感測模型（看不見的敵人無法被選為目標），而這屬於 Phase 5 的 Observation Contract。

當 Phase 5 落地，sensor_failure 應該改為作用在觀測上而不是命中率上。屆時同一個變量名的意義會改變，舊的 failure map 與新的不能直接比較。如何處理這個版本斷層，留給 Phase 5。

## 8. 一句話

> Phase 9 讓方案可以被故意弄壞上千次，而最重要的一步發生在寫程式之前：先量出基線只有 63%、壞天氣反而保護守方、替代部署撐得更久，這些數字讓設計接受了「看起來不對但其實是對的」結果；之後的兩個測試缺口則再次證明，規則的測試資料必須能區分有這條規則與沒有。
