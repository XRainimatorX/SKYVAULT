# Phase 12 回顧

External System Interface v1.2

這份文件檢討**流程**，不檢討人。所有問題都以「什麼樣的做法讓這件事得以發生」來描述 —— 目標是讓下一個階段不要重蹈，不是追究誰的責任。

寫完不再更新。

---

## 1. 摘要

Phase 12 交付了兩份契約、handoff、衝突的分支與決定、九個系統 adapter、外部 API 與 CI 步驟。模擬不變，沒有重工。中途 container 重啟過一次（PostgreSQL 需要重新確認、對話被摘要），計畫照舊繼續。

這一輪最值得記下的是：**測試全綠之後，打開輸出才看到三個錯誤的陳述** —— 星衞「不可行」其實是格子被佔、handoff 在平手時點名一個分支、provenance 沒有 scenario。三個都是程式在自己的意義下「正確」、在讀者的意義下錯誤。

**核心教訓：交給決策者的輸出，要以那個讀者的眼光讀一遍 —— 每個「可行 / 不可行」「最高」「缺口」都問一句：一個不看程式的人讀到這句，會不會以為了一件不是事實的事。**

## 3. 做得好的地方

### 先寫「違反規則的程式」

開設時就讓 SKYVAULT、TAC_ANGEL、STARTX、空字串各自去決定 conflict（Phase 6 回顧改法 1）。這組測試在步驟 C 抓到了決定順序的錯：已決定的 conflict 讓 SKYVAULT 拿到 404 而不是 403。

### 觸發率依測量，而不是依名字

「高風險」最直接的對應是 verdict risky / fail —— 94% 的 run，handoff 會變成雜訊。開設時量了才改用 Phase 7 的旗標（28%）。每個觸發都有一場真實的 run 觸發、一場不觸發。

### 本機逐字執行 CI 步驟

Phase 11 回顧改法 4 的第一次實踐：External systems 步驟的 `/finish` 被送成 GET，本機一跑就 405。推送之前修好。

## 4. 出了什麼問題

### 問題 1：輸出的陳述與事實不符，測試沒有抓到

星衞的 `feasible: false` 來自「Move target occupied」；handoff 的「Highest win_rate: branch TAC_ANGEL:1 (0)」是平手；EIDEN 的 provenance 沒有 scenario_id。測試都通過 —— 它們斷言的是程式算出來的東西。

### 問題 2：一個輸入讓 run 崩潰，存在了好幾個 Phase

`move_range: 0` 讓軍事 policy 在空序列上取 min()。Phase 13 以來沒有一個 scenario 有不能移動的單位；是星衞的 profile 第一次讓「裝備」成為輸入。

### 問題 3：兩套測試同時跑在同一個 PostgreSQL

為了省時間，3.10 venv 在背景跑、/tmp 在前景跑；兩邊的 fixture 各自 DROP 同一組表，11 個 `[postgres]` 失敗。

### 問題 4：反向驗證有三個存活

TAC ANGEL 的拒絕不分系統、EIDEN 的排序含 all_intel、provenance 的補值 —— 三條守護都沒有一個會因為它被拿掉而失敗的測試。

## 5. 根本原因

### 成因 1：測試的期望值是從程式的輸出抄來的

寫測試時先跑一次、看到數字、把數字寫進斷言。這驗證了「程式做它做的事」，沒有驗證「這句話對讀者是真的」。「不可行」的定義從來沒有被寫下來，只有被算出來。

### 成因 2：新的輸入來源沒有先掃過邊界值

外部系統是第一個能任意設定單位能力的來源。開設時測量了衝突與觸發率，沒有對新的輸入（能力為 0、空路線、地圖外）先跑一輪。

### 成因 3：外部服務被當成無狀態的

Redis 與 PostgreSQL 在測試裡是共享的狀態；「平行跑兩套」只在每套各用自己的資料庫時才安全。

### 成因 4：測試的資料剛好滿足兩種寫法

reference 上 TAC ANGEL 命令的單位沒有被別的系統拒絕過；只有一個情報參數時 all_intel 不存在；adapter 自己補了 provenance。測試資料沒有能區分「對」與「拿掉守護」的情況。

## 6. 下一階段要改的事

### 改法 1：輸出的每個判斷詞先寫定義，再寫測試

「可行」「最高」「缺口」「成功」—— 每個交給讀者的判斷詞，在 adapter 或 view 的 docstring 寫下它的定義，測試至少有一個「看起來像但不是」的反例（例如格子被佔 ≠ 不可行）。Phase 14 的城市治理與物流有大量這類詞。

### 改法 2：新的輸入來源先跑邊界值

一個能設定參數的新來源（domain pack、外部提交、UI 表單），開設時把每個數值參數的 0、負數、極大值與空集合各跑一次，崩潰的先修。

### 改法 3：用到外部服務的測試套件一次只跑一套

需要平行時給每套各自的資料庫（不同的 PostgreSQL database、不同的 Redis db 編號）。

### 改法 4：守護的測試資料要能區分兩種寫法

寫一條守護時同時想：「把它拿掉，哪個測試會失敗？」沒有就造一個會讓兩種寫法結果不同的輸入。反向驗證仍然要跑，但不該是第一次想這件事的時候。

## 7. 沒有結論的一項

**權威名單要不要由政策擴充。**

§6 第 8 項寫「預設 NEXUS、SOVEREIGN；政策可加」。authority_handoff 與 open_conflict 收 authorities 參數，但沒有一個設定檔可以改它：governance 契約是 §15 的算力治理欄位，權威放進去會混淆兩件事；另開一份「授權」設定又是第 24 份契約。Phase 19（商用 / 雙軌）會有不同的決策者，留到那時一起決定。
