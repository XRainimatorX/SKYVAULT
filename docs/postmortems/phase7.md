# Phase 7 回顧

Evaluation Engine v0.7

這份文件檢討**流程**，不檢討人。所有問題都以「什麼樣的做法讓這件事得以發生」來描述 —— 目標是讓下一個階段不要重蹈，不是追究誰的責任。

寫完不再更新。

---

## 1. 摘要

Phase 7 交付了 11 軸評估、第 12 份契約、五項防刷分檢查與 trade-off report，event memory 一筆都沒變，沒有任何一輪重工。Phase 3 回顧的五條改法中，四條用上了（第五條「stash 後清 bytecode」這次沒有用 stash），其中兩條直接改變了結果：

```text
改法 1（新能力用觸發它的資料測）   揭露了一個在實際資料上永遠不會觸發的門檻
改法 3（語意與簽名分開對照）       在 commit 前抓到一個偏離凍結定義的指標
```

這一輪最值得記下的是一個新的問題類型：**評估的參數（門檻、權重）也是程式的一部分，也需要用真的資料驗證。** 一個門檻寫在 JSON 裡、契約檢查通過、單元測試用手調的值觸發 —— 但在真實的 run 上它從來不會觸發。

**核心教訓：設定值和程式碼一樣會「看起來有測試、實際上沉默」。每個門檻都要有一場真實的 run 證明它會觸發，也要有一場證明它不會亂觸發。**

## 3. 做得好的地方

### 「每步結束時哪些測試是綠的」寫在 issue 裡（Phase 3 改法 4）

開設時就寫下 A、B 結束時 engine 不接線、輸出不變；C 才改契約與接線。三步都在寫好的狀態結束，沒有出現 Phase 3 那種「A 與 B 分不開」。

### 評估與 exporter 同級

把評估定位成「紀錄的推導」而不是「模擬的一部分」，帶來三個好處：event memory 不變（SCENARIO_END 保留原本的摘要）、評估可以不重跑就換 profile、分層測試可以直接沿用 exporter 的規則。

### 用真的 run 測刷分

三種刷分行為的測試都用引擎跑出來的 run，沒有一個是手造的 event memory。這讓測試同時驗證了「資料長這樣時會觸發」與「這樣的資料真的會出現」。

### 手算對照寫在測試裡

RED 視角的 10 個可計算軸，期望值是手算後寫進測試的，註解寫了計算依據（111 傷害 / 97 hp、40 / 97 hp 損失…）。之後任何人改指標，都能看到原本的數字從哪裡來。

## 4. 出了什麼問題

### 問題 1：一個永遠不會觸發的門檻（最嚴重）

hidden_risk 的門檻 0.5 在 profile commit 時就決定了，契約檢查通過。單元測試若用手調的門檻，也會觸發。但在 reference scenario 的 300 個 seed 裡，沒有一場會讓它觸發。

它是在找「真實的刷分 run」時才被發現的。如果測試用的是手調門檻的 profile，這個問題會一直存在。

### 問題 2：寫指標時順手「改進」了定義

failure_resistance 寫成了 (first − 1) / final，理由聽起來合理，但不是凍結的定義。這次在 commit 前抓到，但它說明：**寫程式的人會自然地「改進」規格**，即使規格是自己幾小時前寫的。

### 問題 3：無效的反向驗證變異

`sed '1a'` 插在多行 docstring 裡。測試全綠，差點被解讀成「分層測試抓不到」。

### 問題 4：凍結文件裡的數字沒量就寫

「result package 大了約三成」—— 實際 5%。在凍結前發現了，但它本來會永遠留在 ADR 裡。

## 5. 根本原因

### 成因 1：設定值被當成資料，不被當成程式

profile 是 JSON，被契約檢查「形狀」，但沒有人檢查「這個值在實際資料上會產生什麼行為」。程式碼有反向驗證的要求，設定值沒有。

### 成因 2：凍結定義與實作者的直覺衝突時，沒有明確的處理方式

改法 3 能抓到偏離，但偏離發生的原因是「實作者覺得另一個定義更好」。這種時候應該做的是：照凍結定義寫，另外在 ADR 提出修改建議 —— 而不是直接寫成自己覺得對的版本。

### 成因 3：反向驗證只看結果，不看變異是否生效

變異插入後只看測試紅或綠，沒有確認插入的程式碼真的會被執行。

### 成因 4：凍結文件的數字沒有出處要求

完成報告的數字大多是從命令輸出貼上的，ADR 的那一句是憑印象寫的。

## 6. 下一階段要改的事

### 改法 1：每個門檻都要有觸發與不觸發的真實 run

設定值（門檻、權重、上限）出現在 profile、rule_set 或任何設定檔時，測試要有：

```text
一場真實的 run 讓它觸發
一場真實的 run 讓它不觸發
```

找不到觸發的 run 時，不是去調測試，而是回頭問門檻是否合理。

### 改法 2：想改凍結定義時，照寫並提案

實作時覺得凍結定義不好，**照凍結定義寫**，在 ADR 寫「建議修改」並說明理由，由下一個 Phase 或使用者決定。

### 改法 3：反向驗證的變異要確認被執行

插入變異後，先確認它被執行到（例如變異是 import 時，`python3 -c "import 該模組"` 應該失敗或產生副作用），再看測試結果。

### 改法 4：凍結文件的數字都要有命令出處

完成報告與 ADR 裡的每個數字，都要能指出是哪個命令的輸出。寫不出命令的數字，量了再寫。

---

## 7. 沒有結論的一項

**profile 的門檻只能用一個 scenario 校準。**

balanced 與 tactical 的所有門檻都是在 tactical_reference_001 上決定的。它是一個對稱的 3 對 3 小規模戰鬥，沒有資源、沒有修復。在 logistics 或之後的 domain scenario 上，這些門檻可能完全不合適。

這需要更多 scenario 才能處理，最早是 Phase 10（批量模擬）或 Phase 13（domain pack）。在那之前，門檻是經驗值，ADR 007 已經這樣標記。

---

## 8. 一句話

> Phase 7 的評估只讀紀錄，所以 event memory 一筆都沒變；Phase 3 的改法讓一個偏離的定義在 commit 前被抓到、讓一個永遠不會觸發的門檻在測試時被揭露 —— 後者說明設定值和程式碼一樣會「看起來有測試、實際上沉默」，所以每個門檻都要有一場真實的 run 證明它會觸發。
