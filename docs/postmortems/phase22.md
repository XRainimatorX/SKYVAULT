# Phase 22 回顧

## 1. 起因

使用者問「你真的覺得你完成了我給你的文件嗎？」。答案是：完成了開發總計劃，但總計劃是從 Formal Spec 與 Definition 推導出來的二手文件，而驗收一直以它為準。總計劃把原文的格式改寫過（扁平的 scenario、自己的 11 個評估軸、攤平的 handoff），也略過了原文的幾整塊（§21 Phase I、三角包、CYBERHOUND、§14.2 的大部分列）。每一個 Phase 都「通過驗收」，整體卻沒有對齊最上游的規格。

## 2. 做得好的

- 開設時逐節對照原文測量，把「一致 / 不一致 / 沒有」寫進 issue，後面每一步都回到那張表。
- 契約逐欄的驗收用的是從原文抽出的欄位，而不是再寫一次的摘要；抽出後第一次比對，除了範例內容之外全部吻合。
- 新的城市模型全部是 opt-in：既有的 scenario 逐位元不變，hash 只在格式與評估改變時移動，而且每次都比對過事件。
- 驗收真的跑系統：三角包、接管四分支、危機世界都在驗收的服務上跑完。

## 3. 做得不好的

- **測到別的副本。** 本機 CI 的乾淨副本以 editable 安裝，之後的全套測試在測那個副本；我花了一輪才發現。
- **先推送、後跑 CI。** 51ff0ac 在本機 CI 之前推送，GitHub CI 紅在一個改名後沒有更新的 CI 斷言。
- **phase 時鐘只測了時鐘本身。** 步驟 K 加了 PhaseEventClock，但沒有一個 domain 真的在上面跑過，等到 §2.3 的世界才發現城市的計時全部以 tick 比對。
- **fixture 沒有走到的分支。** §9.2 的測試用 fixture 跑，fixture 的 AEROGRID / HADES 不在空域，空域路徑的錯誤留到驗收才出現。
- **測試期間改檔。** 全套測試跑的時候改 src，讓結果混進一半的改動。

## 4. 根因

驗收的來源是「最近的一份規格」，而不是「最上游的那份」；每一層推導都可能改寫或遺漏，而以推導文件驗收看不到這些差異。工程上的幾個失誤則都是同一件事：驗證的對象不是我以為的那個（別的副本、別的分支、fixture 沒走到的路徑、跑到一半的檔案）。

## 5. 學到的

```text
1. 驗收要回到最上游的文件，並把它變成可執行的清單（spec_acceptance.json、spec_fields.py）；推導文件只當回歸
2. 每次驗證先確認對象：import 的是哪個副本（印 __file__）、跑的是哪個 commit、fixture 走到哪個分支
3. 新的基礎能力（時鐘、空間）要有一個 domain 在上面跑完整場，而不只是單元測試
4. 推送前逐步跑 CI；改名時 grep 整個 repo，包括 .github/
5. 全套測試跑的時候不改它會讀的檔案
```

## 6. 下一個 Phase 的改法

- 開設時先列「驗收來源」與它的上游文件；驗收清單的每一條寫明上游章節。
- 本機 CI 改成每次都在自己的 venv 裡跑，不動系統的安裝。
- 每個 adapter 的測試同時走 fixture 與每一個 domain 路徑。
