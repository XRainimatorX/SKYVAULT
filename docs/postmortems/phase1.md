# Phase 1 回顧

Core Contract Pack v0.1

這份文件檢討**流程**，不檢討人。所有問題都以「什麼樣的做法讓這件事得以發生」來描述 —— 目標是讓下一個階段不要重蹈，不是追究誰的責任。

寫完不再更新。

---

## 1. 摘要

Phase 1 交付了 11 份契約、四個強制驗證點、11 份 JSON Schema，修正了 Phase 4 留下的缺陷，模擬行為沒有改變，沒有任何一輪重工。

但過程中發現：**上一階段回顧裡建議的修正測試，其實抓不到它要抓的缺陷。** 如果照抄而沒有實際驗證，Phase 1 會帶著一個「看起來有測試」的缺陷繼續往下走。

**核心教訓：一個測試是否有效，只能把缺陷放回去跑一次才知道；寫下來的建議、甚至寫在回顧裡的建議，都不能代替這一步。**

## 3. 做得好的地方

### fixture 在任何程式碼之前 commit

Phase 4 的共同基準 issue 指定了 `tests/fixtures/` 的路徑，但從未建立，各組只能自己在測試裡寫 sample。

這次 fixture 是開設的最後一步，在第一行契約程式碼之前就進了 repo。**三個步驟、56 個契約測試全部對著同一份形狀寫**，沒有出現兩個步驟對「合法的 event 長什麼樣」理解不同的情況。這個做法應該保留。

### 寫入時驗證，讓巢狀化遷移變得安全

`record_event()` 在 event 進 event_memory 之前先通過契約。改 `to_dict()` 的那一刻起，任何一個形狀不對的 event 都會讓模擬當場停下，而不是寫出一份壞的 event_memory、等到某個 exporter 讀它時才出錯。

**驗證點放在資料產生的地方，而不是使用的地方，錯誤就會在最接近成因的位置浮現。**

### 用上一階段的報告數字驗證遷移

exporter 遷移完成後，沒有只看測試綠燈，而是把輸出數字與 Phase 4 報告逐一對照：entity_history 21 筆、causal_chain 46 條、replay 12 個 state。三個都一致，證明遷移只改了讀取方式、沒改行為。

**凍結報告裡記下的具體數字，成了下一階段的回歸基準。** 這是 Phase 4 報告寫得夠具體的直接回報。

### 規格先進 repo

上傳的規劃文件不在 repo，換了工作環境之後也不在磁碟上，只存在對話紀錄裡。開設時第一件事就是把 Phase 0–20 的原文規格與 Formal Spec 的契約格式寫進 `docs/plan/`。之後的每個 Phase 都有一份不會消失的正本。

## 4. 出了什麼問題

### 問題 1：上一階段建議的測試是無效的（最嚴重）

Phase 4 回顧的「改法 3」寫了一個測試，並斷言它「在現在的程式碼下會失敗 —— 它抓得到問題 4 的缺陷」。

**它抓不到。** 子字串 `(damage = 10)` 被另一筆非致命攻擊滿足了。照抄的話，Phase 1 會有一個綠燈的測試、一個仍然存在的缺陷，以及一份聲稱兩者相反的回顧。

這次沒出事，是因為測試寫完後把缺陷放回去跑了一次。

### 問題 2：工具環境不一致

`mypy src/` 報出五個 import 錯誤，實際上程式碼沒問題 —— PATH 上的 mypy 是另一個隔離環境。花了一輪排查才確認。

**沒有 CI，就沒有一個「標準環境」可以拿來判斷誰對。** 每個人的機器都是自己的真相。

### 問題 3：Spec 的矛盾在寫程式時才發現

Formal Spec 對 assumption_registry 與 data_provenance 各給了兩種形狀。這兩處都是寫到那份契約時才注意到，決定在寫程式的當下做出，事後才補進 ADR。

### 問題 4：凍結文件在凍結當下就已過時

`phase4_tactical_slice.md` 的兩個函式簽名在凍結時就與程式碼不符。凍結文件依規定不修改，所以它會永遠帶著這兩處錯誤。

### 問題 5：上一階段的收尾沒做完

Phase 4 的 milestone 在 PR 合併兩個月後仍然 open；三份 issue 的格式彼此不一致。兩者都不影響功能，但都說明「收尾」沒有一份會被逐項核對的清單。

## 5. 根本原因

### 成因 1：建議沒有被執行過

問題 1 的測試是在回顧裡「寫出來」的，從來沒有被跑過 —— 回顧寫於缺陷決定不修之後，沒有程式碼可以拿來驗證它。

**寫在文件裡的程式碼，和跑過的程式碼，是兩件事。** 這和 Phase 4 的「檔案存在不等於內容正確」是同一個教訓的另一面。

### 成因 2：開設步驟不包含「讀規格找矛盾」

開設的清單是：規格文件、milestone、issue、fixture。它要求把規格**抄進來**，但沒有要求把規格**讀一遍、列出矛盾**。於是矛盾只能在寫到那裡時才被撞見。

### 成因 3：凍結與收尾都沒有驗證步驟

凍結文件時，沒有人比對它的內容與程式碼；關閉 Phase 時，沒有人逐項核對 milestone 與 issue。兩件事都是「做了就算完成」，沒有「確認做對了」那一步。

## 6. 下一階段要改的事

### 改法 1：抓缺陷的測試必須做反向驗證

在 issue 的 Final Done Criteria 加上：

```text
N. 每個為抓特定缺陷而寫的測試，都把缺陷放回去跑過，確認它會失敗
```

完成報告裡記錄做過反向驗證的測試清單。

### 改法 2：CI 作為標準環境

Phase 1 已加入 `.github/workflows/ci.yml`。之後「測試過不過」以 CI 為準，本機結果只是參考。

### 改法 3：開設時列出規格矛盾

開設清單加一步：讀該 Phase 對應的 `docs/plan/` 與 `docs/plan/formal_spec.md` 段落，把矛盾與待決定事項寫進 issue 第 6 節，**在寫程式之前就做出決定**。

### 改法 4：凍結前比對、收尾時核對

```text
凍結文件前    grep 文件裡出現的每個函式簽名，比對程式碼
關閉 Phase 時  milestone 關閉、issue 全部關閉、issue 格式符合十二節
```

## 7. 沒有結論的一項

**套件仍然不可安裝，tests 與 scripts 還是靠 `sys.path`。**

Phase 1 在 `pyproject.toml` 加了 `[project]` 與相依宣告，離可安裝只差 build-system 與 src 佈局設定。但那會改變所有人的執行方式，不屬於契約的範圍，所以再次延後。

代價：每個新的測試或腳本都要複製那段 `sys.path` 區塊，ruff 的 E402 豁免也要跟著擴充 —— 這一輪就因為新的 `tests/contracts/` 子目錄而改了一次。

## 8. 一句話

> Phase 1 的契約做對了，測試先於程式、驗證放在資料產生的地方、上一階段的數字被拿來當回歸基準 —— 但它也證明了寫在回顧裡、從沒被跑過的測試建議可能是錯的；有效與否只能把缺陷放回去跑一次才知道。
