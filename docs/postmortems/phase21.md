# Phase 21 回顧

Standalone SKYVAULT v2.1 —— roadmap 之後的第一個 Phase

這份文件檢討**流程**，不檢討人。寫完不再更新。

---

## 1. 摘要

Phase 21 把 SKYVAULT 從「一組腳本加一個參考切片」變成「一個指令就是完整系統」。同一輪開頭先修了 code review 的十項發現。

最值得記下的是：**二十個 Phase 都建在一個開發用的切片上，而它悄悄地成了系統的一部分。** 引擎以它命名、沒指定時退回它的 policy、驗收以它為基線、介面只讀它的腳本寫出的資料夾。沒有一個 Phase 決定要這樣；每一個都只是「先用 reference 跑」。

**核心教訓：開發用的東西要有一條明確的界線，而且要有測試守住 —— 否則它會一個預設值接一個預設值地長進系統裡。**

## 3. 做得好的地方

### 先量再選基線（Phase 15 改法）

計劃寫的基線在沒有壓力時就崩潰；量四個候選只花一分鐘，避免了一張第一級就斷的 failure map。

### 測試取得參考切片的方法就是部署的方法

沒有替測試開後門：`SKYVAULT_SCENARIO_PATH`、`SKYVAULT_POLICY_MODULES` 是正式功能，測試、開發腳本、子程序都用它 —— 也因此 RQ worker 與腳本子程序不需要特別處理。

### 守護測試有反例

「系統不提參考切片」的測試先植入一個檔案確認自己抓得到，再檢查真正的 repo。

## 4. 出了什麼問題

### 問題 1：預設值的累積

一個切片從「第一個能跑的東西」變成引擎的名字、退回的 policy、所有腳本與驗收的預設。

### 問題 2：一個從來不會失敗的分層測試

`node.module.startswith("..service")` —— 相對 import 的 module 名稱沒有點，這個測試從 Phase 11 起就是空的。

### 問題 3：存了再讀才露出的順序問題

比較報告依 dict 的順序列指標；只要結果經過 sort_keys 的 store，順序就變了 —— 介面改讀 store 才第一次發生。

### 問題 4：CI 步驟在髒的工作目錄裡跑

第一次在本機逐字跑 CI 時，`runs/registry.jsonl` 的歷史讓一個斷言失敗 —— CI 的機器是乾淨的。

---

## 5. 根本原因

### 成因 1：「先用 reference」沒有期限

每個 Phase 都合理地拿現成的切片當預設，沒有一個 Phase 負責把它拿掉。

### 成因 2：沒有看過分層測試失敗一次

Phase 20 改法 2（每個檢查先看它失敗一次）只用在驗收檢查上，沒有回頭用在既有的分層測試。

### 成因 3：輸出只在記憶體裡比較過

報告的測試都用剛算出來的物件，沒有一個經過 store 的往返。

---

## 6. 之後要改的事

### 改法 1：開發用的東西放在開發的位置，並以測試守住界線

`tests/fixtures/`、`scripts/dev/`；系統的檔案不得提它們（`tests/test_standalone.py`）。

### 改法 2：每個結構測試都要有一個讓它失敗的反例

尤其是以 AST 判斷 import 的測試：相對 import 要以 level 解析。

### 改法 3：會被存起來的輸出，測試要經過一次存取往返

JSON 的 sort_keys、tuple 變 list，都會改變依賴順序或型別的輸出。

### 改法 4：本機逐字跑 CI 時用乾淨的複本

`git ls-files` 打包到暫存資料夾、`git init`，再跑。

---

## 7. 一句話

> 二十個 Phase 都站在同一個開發用的切片上，它就悄悄長成了系統的骨架 —— 開發用的東西要放在開發的位置，並且用一個會失敗的測試守住那條界線。
